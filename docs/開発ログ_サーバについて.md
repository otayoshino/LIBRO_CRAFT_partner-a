### 作業内容

#### Libro連携機能の計画書作成

**概要**
- ContentsBuilder（オーサリングUI）で作成したアノテーションを、実際のLibroが読み込めるbook形式へ書き出すための計画書を新規作成
- 保存先：`libro_integration/計画書.md`（既存リポジトリを汚さないよう新規ディレクトリに配置）

**調査して判明した仕様**
- bookフォルダ構成：`index.json`（ページ一覧・目次）、`p####.json`（ページごとのテキスト・OCR座標・アノテーション）、`annots/`（アノテーション画像、平文PNG）、`sounds/`（音声、暗号化mp3）、ページ画像（暗号化jpg）
- 暗号化方式（Pbve2000）：先頭8バイト`Pbve2000`ヘッダー＋データ全体を`0xCC`でXOR。対象はページ画像・音声のみ。`annots/`のPNGは平文でよい
- `annots[]`要素のスキーマ：`filename` / `rect` / `hidden` / `actions`
- 確認できた`actions`の種類：`GoTo`+`FitPage`（ページリンク）、`URI`（外部リンク）、`Launch`（音声再生）、`Hide`/`Show`（表示切替）
- 付箋（テキストノート）はLibro側に専用action型が無いため、「閉じたアイコン」「開いた状態（テキストを画像化したもの）」の2枚をHide/Showで切り替える方式で実現する方針
- 実サンプルは `book_samples/` ディレクトリ配下に配置済み（git管理対象外として運用中、`.gitignore`済み）

**今回決定した設計方針**
1. JSONモジュールは**インポート/エクスポート双方向**対応にする（既存bookの再編集に対応するため）
2. ContentsBuilderが理解できない未知のアノテーション（actionsの組み合わせ）は**編集不可・削除しない**で保持し、書き出し時もそのまま残す（Libroは開発が活発で、想定外データが混在し得るため）
3. ContentsBuilderが管理しているアノテーションを削除した場合は、対応する`annots/`画像・`sounds/`音声ファイルも**同時に削除**する（ゴミファイルを残さない）
4. 削除済みアノテーションIDは**再利用しない**（常に「使用中の最大ID + 1」を新規発行。過去の参照との衝突を避けるため）
5. 現状の bookフォルダのzipダウンロード/アップロードは**暫定運用**。最終形ではContentsBuilderがLibro本体に組み込まれ、Libroのbookストレージへ直接アクセス（API等）する構成を目指す。データの変換ロジック（JSON入出力・暗号化処理）はzip運用・API直結のどちらでも共通して使える設計とする
